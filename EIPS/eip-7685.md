## Abstract

* goal
  * 👀general purpose framework -- for -- storing contract-triggered requests👀
    * execution header is extended -- with -- 1! field / store the request information
    * requests are exposed -- to the -- consensus layer / processes EACH one

## Motivation

* smart contract controlled validators
  * -> high demand -- for -- ADDITIONAL EL triggered behaviors
  * delegate administrative operations -- to -- their governing smart contracts 
    * -> creates a safer system | end users
    * Reason: 🧠
      * avoid intermediaries needing to step in
      * ensure certain operations occur🧠

* abstract EACH individual request details -- from the -- EL + add NEW request types
  * simpler
  * NOT require an update | execution block structure

## Specification

### Execution Layer

#### Requests

```
requests = request_type ++ request_data
```

* `request_type`
  * define its OWN `requests` object / its own `request_data` format
  * 1 byte
* `request_data`
  * opaque byte array
  * \>=0 encoded request objects


#### Block Header

* `requests_hash`
  * 32 byte
  * uses
    * extend the header
  * steps to compute it
    * build an intermediate hash list -- by -- hashing ALL block requests list's non-empty requests elements /  
      * if item has empty `request_data` (== has ONLY `request_type`) -> excluded from the list
      * items MUST be ordered -- by -- `request_type` ascending
    * sha256 hash (INTERMEDIATE element hashes) 

    ```python
    def compute_requests_hash(block_requests: Sequence[bytes]):
        m = sha256()
        for r in block_requests:
            if len(r) > 1:
                m.update(sha256(r).digest())
        return m.digest()
    
    block.header.requests_hash = compute_requests_hash(requests)
    ```

* | process a block,
  * MULTIPLE `requests` objects / DIFFERENT `request_type`s will be
    * produced -- by the -- system
    * accumulated | block requests list

## Rationale

### Opaque byte array -- rather than an -- RLP array

* `request_data` array get -- from -- opaque bytes' second byte vs RLP (or other encoding) list
  * pros
    * -> | future, we can support DIFFERENT encoding formats -- for the -- request payload
      * _Examples:_ SSZ, LEB128, or a fixed width format

### Request source and validity

* TODO:This EIP makes no strict requirement where a request may come from nor when/how a request must be validated
* This is to provide future protocol designers maximum flexibility.

The authors' recommendations on source and validity of requests are:

* The source of requests should be from the execution of transactions
  * More specifically, transactions which make calls to designated system contracts
    that store the request in account
  * The storage would later be retrieved by a
      post-block system call to the contract
  * Alternatively, if the system call does
        not need to be inherently concerned with rate limiting, it could rely simply
        on emitting an event which is later parsed post-block by the system and
        converted into a request.
* A request's validity can often not be fully verified at the execution layer.
  This is why they are referred to merely as "requests"; they do not carry the
  authority on their own to unilaterally catalyze an action
  * We expect the system
    contracts to perform whatever validation is possible by the EL and then pass
    it on to the CL for further validation.

### Ordering

The ordering across types is ascending by type. This is to simplify the process
of verifying that all requests which were committed to in `requests_hash` match.

An alternative could be to order by when the request was generated within the
block. Since it's expected that many requests will be accumulated at the end of
the block via system calls, this would be difficult to enforce. Therefore,
ordering by type is the most straightforward ordering which ensures integrity.

#### Intra-type

Within the same type, order is not defined. This is because the data of the
request is opaque as far as this EIP is concerned. Therefore, it is to be
determined by each request type individually.

### Removing empty requests in commitment

We exclude empty requests elements from the `requests_hash` commitment in order to get a
stable 'empty' hash value that is independent of the blockchain fork. For a block with no
requests data, the `requests_hash` is simply `sha256("")`.
